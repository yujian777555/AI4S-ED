## 1. 建设背景与需求映射

电渗析（ED）是绿色化工中水盐分离、酸碱回收、物料提纯的关键电膜过程。科研与工程上的痛点：

1. **知识碎片化**：文献/专利/实验数据/仿真结果模态多样（文本、I-V 曲线、EIS 谱、SEM/EDX 图、时序数据），难以统一检索与复用；
2. **方案依赖专家经验**：创新方案提出缺乏系统性检索+机理约束，且难以评估“创新性/可行性”；
3. **通用大模型幻觉**：直接问答不可信（编造文献、虚构数据、违反电化学机理）；
4. **实验验证链路长**：从方案到干/湿实验、数据回流缺乏平台化编排，经验无法沉淀为知识资产。

### 1.1 用户需求 → 设计要素映射

| # | 用户需求 | 对应设计 | 落地章节 |
|---|---|---|---|
| R1 | 文献自动调研、整理、入知识库 | 文献调研 Agent + 多源检索 + 解析/抽取/策审入库流水线 | 03 |
| R2 | 基于知识库问答且**不产生 AI 幻觉** | 证据锚定生成、禁答（Abstain）策略、机理约束校验器、交叉核验 | 02/03/07 |

| R4 | 多模态数据**统一表征** | 统一科学数据对象 **USDO** + 领域本体 **EDDO** + 跨模态统一向量空间 | 02 |
| R5 | **机理与数据双驱动**、垂域模型 + DeepSeek Harness | 机理模型族 MM（MEM-0~4）+ 数据驱动层 DD（代理模型/PINN/垂域微调）+ DSH 底座 | 04/08 |

### 1.2 顶层设计原则

1. **证据锚定（Evidence-Anchored）**：一切面向用户的科学结论必须带可回溯证据引用（文献条目 / USDO / 仿真任务 / 实验记录）；
2. **机理优先（Mechanism-First）**：任何方案先过机理约束（物料/电荷平衡、极限电流、Donnan 等），数据驱动只允许在机理允许的邻域内外推，越界必须标注不确定性；
3. **双智能体对抗（Adversarial Peer Review）**：创新性与可信性由“提案—评审”对抗博弈收敛，杜绝单模型自说自话；
4. **人机协同分级（Human-in-the-Loop by Level）**：起步为“建议—强校验—人裁决”，逐步向设备自动化（LabLink）演进；
5. **全链路溯源与版本化**：知识、模型、实验、案例均可追溯、可回滚；
6. **评测先行**：幻觉率、证据可验证率、创新性等指标从 MVP 起即纳入看门狗（见 07）。

## 3. 核心业务闭环（数据流）

### 3.1 闭环①：文献知识闭环（调研 → 入库）

```
多源检索(Crossref/arXiv/S2/CNKI/专利…)  ──►  lit_researcher 调研Agent(主题扩展+去重+相关性筛选)
      │
      ▼
解析管线：PDF→文本/表格/公式(GROBID/Nougat/MinerU) + 图表对象化(图→图元数据)
      │
      ▼
多模态抽取：实体/关系/工况/指标/方法 → 映射到 EDDO 本体（USDO 化）
      │
      ▼
knowledge_curator 策审Agent：证据完备性/冲突检测/质量评分 → 人工抽检口
      │
      ▼
知识库原子提交：图谱三元组 + 语料分块 + USDO(含统一向量)  → 版本化快照
```

**产物**：可检索、可引用、带溯源的知识资产；任何 claim 均可回指“文献 ID + 位置 + USDO ID”。

### 3.2 闭环②：问答-方案闭环（双智能体对抗）

```
用户问题 / 科研目标 ──► 主控 orchestrator：意图理解 → 任务分解 → 分步调度 → 汇总输出
      │
      ▼
      ┌─────────────── RADE 双智能体对抗引擎 ───────────────┐
      │  ① proposer 提案官                                 │
      │     检索 KB(图谱+向量) + 网络检索 + 机理模型快查      │
      │     → 生成候选方案(含机理链条/预期指标/证据)          │
      │         ▲ 迭代(≤N轮, 见05)             ▼            │
      │  ② critic 评审官                                   │
      │     合理性/可行性(机理约束+资源)/创新性(与知识库先验  │
      │     对比)/可验证性 评分 + 缺陷清单                    │
      └──────────────────────────────────────────────────┘
      │（分歧不可收敛 → orchestrator 提请人工仲裁）
      ▼
结构化交付：科学假设卡 SSH（含：假设、机理、创新点、预测区间、不确定性、验证实验要点、证据清单）
```

**反幻觉强制**：SSH 中每个科学数字声明必须携带证据引用或机理模型输出；无证据则显式标注“待验证假设”。详见 05/03。检索统一走 **RAG 两段式**（召回 → 薄精确层查准 → 证据锚定生成，见 02 §5.0/03 §6）：向量/关键词负责“找”，SQLite 断言表等精确层负责“查准”，生成端不越权编造。

### 3.3 闭环③：实验验证闭环（干实验 → 湿实验 → 验证）

```
SSH ──► exp_designer 实验设计Agent：DoE/Bayesian优化 → 实验矩阵 + 可测指标
      │
      ▼
dry_lab_runner 干实验执行Agent：数字孪生/CFD/机理模型批量求解（自动、队列化、可复现）
      │
      ▼
干实验报告 DER：预测性能窗口、灵敏度、可行域 → 若机理预测矛盾则打回方案层
      │
      ▼
wet_protocoler 湿实验协议Agent：WPP（步骤SOP/耗材/设备/安全/记录表单/预期判据）
      │  人执行（记录：测样、曲线、照片/视频、时序数据）
      ▼
ERP 实验记录包 回传平台（GUI 上传/表单自动校验/LabLink 预留直采）
      │
      ▼
validator 验证Agent：ERP vs SSH/DER 预测比对 → 结论：证实 / 部分证实 / 证伪 / 无效
      │
      ▼

```

### 3.4 闭环④：自进化闭环（知识 → 模型 → 能力）

```
Case(问题+SSH+DER+WPP+ERP+结论+数据) ──► 案例库原子入库
      │
      ├─► knowledge_curator：修正/扩充 EDDO 图谱、更新“经验-事实”断言、冲突消解
      ├─► 触发模型更新：代理模型增量训练 / PINN 再校准 / 垂域检索模型再微调(调度器)
      ├─► 评测看门狗：幻觉率/命中率/创新性分布/预测-实测偏差 监控，越过阈值告警
      └─► 版本快照 + 审计日志（可回滚）
```

### 3.5 记忆子系统（Memory，v0.2 增补）

除 L2 知识库（=长期**语义记忆**）外，增设贯穿 L2/L4/L6 的**记忆子系统**，统一存储智能体的历史操作、问答会话与实验过程，支撑跨会话学习与反思沉淀，是自进化闭环④的新增输入源。

**记忆四级分类**

| 类型 | 存什么 | 生命周期 | 存放 |
|---|---|---|---|
| 情节记忆 Episodic | 一次会话问答、Agent 操作记录（工具调用/检索/决策/失败）、实验执行过程 | 短期~中期（TTL/压缩策略） | 记忆事件流 + EpisodeSummary |
| 语义记忆 Semantic | 图谱/USDO/语料/案例（=现有 L2 知识库） | 长期 | L2 存储三载体（A.5） |
| 程序性记忆 Procedural | 成功可复用的工作流/技能模板 WorkflowRecipe（=可执行技能 Skill 的结构化注册，§3.6） | 长期（评测门禁后入库、版本化） | 记忆库（版本化） |
| 反思记忆 Reflective | 周期反思摘要、重复失败模式、改进建议（ReflectionNote） | 中期 → 沉淀为语义/程序记忆 | 反思记录流 |

**关键数据对象**（登记见附录 A.1）：`OpRecord`（操作记录，Agent 每次工具调用/决策自动落）、`SessionRecord`（会话记录）、`EpisodeSummary`（情节摘要）、`WorkflowRecipe`（技能模板）、`ReflectionNote`（反思记录）。

**记忆生命周期五步**

```
①写入     所有 Agent 操作 / 问答 / 干湿实验事件 自动写 OpRecord、SessionRecord（不可变事件流，与溯源 ID 同链）
   │
②整理     去重 → 压缩 → 聚类 → 事件↔Case 关联 → 生成 EpisodeSummary
   │
③召回     orchestrator 任务启动时按语义相似召回：相似问题历史 / 历史失败(负记忆) / 技能模板
   │        → 注入 Agent 上下文（附溯源）；各 Agent 经 memory_recall 工具调用（05 §7.1）
   │
④沉淀     情节/反思 → 经评测门禁 + 抽检 → 升级为语义记忆或 WorkflowRecipe（版本化）
   │
⑤遗忘治理 TTL / 去重 / 不活跃降权 / 权限隔离（RBAC，同 07） / 隐私清除
```

**防“记忆毒化”规则**：召回的记忆只作上下文提示（标注“历史经验，非事实”）；凡要影响知识库或模型的沉淀必经评测门禁与人工抽检（与 07 一致）；失败模式以**负记忆**进入语义层并优先生效。技术载体见 08 §2（记忆事件并入 SQLite append-only 事件表；向量化摘要入 FAISS 索引）。

**记忆冲突自主仲裁（v0.3 增补）**：当新记忆与旧记忆冲突时，由**记忆仲裁 Agent（`memory_arbiter`，A.3 新增角色，orchestrator 触发）**自主裁决，支持“删旧留新”与“两者都保留”两类走向。规则与边界如下：

1. **先结构化分类，不急于裁决**：
   - **T1 事实冲突**：新旧记忆对同一对象/条件给出互斥断言（如“某膜在 60 ℃ 稳定” vs “已出现降解”）；
   - **T2 条件性冲突**：结论相反但适用条件不同（不同料液体系/浓度区间/膜型号批次）→ 默认不是真冲突，优先**条件化并存**；
   - **T3 偏好/策略漂移**：目标口径变化（优化目标从“最低能耗”转向“最高选择性”）→ 通常“新替旧 + 旧记忆降权归档”。
2. **证据比较器（而非主观感受）**：按 `(来源权威性, 多源支持数, 是否实验 verified, 时效性, 适用域重叠度, 用户目标相关性)` 六因子对两版记忆评分。
3. **自主裁决决策矩阵**（`memory_arbiter` 输出）：

   | 情形 | 裁决 | 执行语义 |
   |---|---|---|
   | T1/T3 且新记忆证据显著更强（如 verified/多源/更新） | **删除旧记忆、保留新记忆** | 软删除：写 Tombstone（墓碑，保留审计与可回滚），旧记忆移出召回面 |
   | T2 条件不同，或 T1 但证据相当 | **两者都保留** | 加适用条件标签并建立关联（并存），召回时按条件匹配路由 |
   | 新记忆证据更弱 | 拒绝替换 | 保留旧记忆，新记忆降权/挂起待更多证据 |
   | 涉及 verified/high 语义事实，或影响安全/关键工艺决策 | **升级人工仲裁** | 不自主删除，走 07 人工仲裁队列 |

4. **删除纪律（防不可逆与防自我强化）**：
   - **任何删除都是软删除 + Tombstone**：记忆记录永不物理抹除（审计、回滚、负记忆溯源需要）；
   - **按类型分级**：提示级记忆（情节/反思）允许 `memory_arbiter` 裁决软删除；**事实级（语义记忆 verified/high）只允许 superseded 标记，绝不 delete**；
   - 重大替换可设**冷静期/观察窗**（如 N 天或 N 次相关召回无回归后再正式生效）；
   - 每次裁决落 `ConflictRecord`（冲突维度、断言极性、条件、证据分、裁决与理由）并纳入反思记忆；看门狗统计“裁决-人工一致率”。
5. **与既有机制分工**：入库知识冲突（02/03 §5）→ `knowledge_curator` 策审；Case 回流冲突（07 §3）→ 知识修订；**记忆自身冲突 → `memory_arbiter`**；三者在“verified 不自动达成 + 证据锚定 + 版本化”上共用同一纪律。

### 3.6 主控编排协议：任务分解 → 分步执行 → 汇总输出（v0.5 增补）

**主控 Agent（orchestrator）与调研 Agent（lit_researcher）在角色上严格分离**（图中分块独立）：

| 角色 | 是 | 不是 |
|---|---|---|
| `orchestrator` 主控 | **调度中枢**：意图理解与问题规约 → 任务分解为步骤计划 → 分步调用专业 Agent/服务 → 跨步骤上下文与产物传递 → **结果汇总与最终输出**；失败重试与仲裁升级入口 | 不做专业执行：不亲自检索/调研、不提方案、不做实验（规划时可调用 memory_recall 召回历史经验作上下文，这不属于“调研”） |
| `lit_researcher` 调研 | **专职资料员**：多源查找文献/专利/标准/网页与内部资料、去重与相关性筛选、研读与总结（检索报告/结构化摘要），并把调研发现按策审通道总结入库 | 不做任务分解与最终汇总输出 |

**编排协议五步**

```
①规约    意图理解 + 约束抽取 → 结构化问题卡 Q（含目标/膜型白名单/物料/指标/预算）
②分解    产出步骤计划 Plan = [Step₁ … Stepₙ]：每步标注 负责Agent/服务、输入产物、验收判据
③执行    按依赖拓扑分步调度（可并行步骤并行）；每步结果写工作区并自动落 OpRecord（§3.5）
④校验    步骤产物过约束校验器/规则（L3）；失败自动重试或回退；跨步冲突升级人工仲裁
⑤汇总    聚合各步产物 → 最终交付（答案 / SSH / 调研报告 / 实验计划 / Case）
```

**示例**（“提出并验证提升单价选择性的方案”）：`Step1 调研 lit_researcher（检索+总结+入库）→ Step2 方案 RADE（对抗生成 SSH）→ Step3 干实验 dry_lab_runner（DER）→ Step4 湿实验 wet_protocoler+人执行（WPP→ERP）→ Step5 验证 validator（结论+Case）→ 汇总输出`。主控只“调度与汇流”，专业内容全部落在对应 Agent/服务；RADE、实验线内部协议（05 §3、06）作为“子流程”由主控按步骤调用。

**技能自进化（主控 Agent 能力扩展，v0.6 增补）**：主控 Agent 在编排职责之上增加“自主编写技能（Skill）并按使用效果沉淀/淘汰”的能力，实现 Agent 层自进化：

1. **识别**：任务/会话结束后，主控分析 OpRecord 与步骤计划——发现“同类任务重复出现、当前无现成 Skill 可复用、人工介入或返工偏高”时，进入技能编写模式；
2. **编写**：从近期成功的 Plan + 产物提炼为 **SkillDraft**（结构化规格：`触发条件 / 适用域(EDDO 标签与工况范围) / 步骤序列(可含工具与 Agent 调用) / 工具与参数 Schema / 上下文提示模板 / 输出契约 / 验收判据 / 评测指标`；对齐 DSH skill 机制，一份 Skill 可包含“提示词模板 + 工具/Agent 序列 + 判据清单”）；
3. **试运行（生成 ≠ 生效）**：SkillDraft 先以**影子模式（shadow）**在真实任务上旁路试运行或离线评测——指标：调用成功率、产物质量分、耗时/成本、下游 validator 结论或用户采纳率；
4. **沉淀或淘汰**：过评测门禁（07）→ 正式入库 **Skill Registry（技能库）= 程序性记忆 WorkflowRecipe 的可执行落地**（版本化、带 owner/来源 provenance/适用域）；未达标 → 修订再试或废弃（supersede）；上线后看门狗持续监控效果：显著劣化 → 自动降级/回滚并触发修订；**高风险技能（涉及实验安全/工艺决策）必须人工审批后才可 active**。

**护栏**：① 技能库去重与相似度检查，避免同质技能堆积；② Skill 内容版本化 + 只读基线（自动生成的修改不得覆盖人工基线，须生成新版本）；③ 技能提示/指令本身防注入审查（同 LLM 网关安全）；④ 每次“编写→生效→淘汰”全程落 OpRecord/审计；⑤ 技能评测指标与看门狗打通（07 §5.3 增列“技能调用成功率”“技能-人工审编比”）。技能自进化闭环与记忆子系统（§3.5）共用“沉淀必经评测门禁”纪律，且不改变“主控不做专业执行”的边界——技能编写是“把已验证的编排/流程固化为资产”，不是让主控替代专业 Agent 干活。

**自进化内核（Evolver）与治理（Governor）分层（v0.11 增补）**：自进化拆为两层——**Evolver（方法内核）**负责“提出改进”，采用 A-Evolve 五步：`Solve（取失败证据：看门狗/OpRecord/评测，脱敏+租户过滤）→ Observe（产出 ObservationReport：错误类别/根因/频率/严重度）→ Evolve（提出 ≤3 个变异：SkillDraft / PromptPatch / KnowledgeEntry(经验级)）→ Gate（特异性/可测性/影响半径/一致性自检）→ Reload（交 Governor 并记 EvolutionLog）`；**Governor（平台治理，不可替代）**负责“放行落地”：影子验证 → 评测门禁 + 全 Agent 回归 → A/B → 版本注册/回滚 → 人工审批闸 → 审计。产物语义：**PromptPatch**（最小系统提示补丁）与 Skill 同生命周期（版本化/回归/回滚/只读人工基线）；**KnowledgeEntry** 只进经验记忆（≤medium、带 src_refs），升级知识库事实仍走策展 + verified 门禁。纪律：观察输入脱敏并按 tenant/domain 隔离；每轮 ≤3 变异、禁模糊技能/一过性改进；进化不改代码/模型/知识库事实/EHS 规则（模型更新仍走 07 §4 重训门禁）。看门狗增列“进化提案通过率”“进化回归回滚率”。（方法论改编自 A-Evolve（A-EVO-Lab）与 AutoResearchClaw 的 `a-evolve` 技能；集成前确认其许可证并标注出处。）

## 4. 关键横切设计

1. **统一溯源 ID**：全平台对象（文献条目、USDO、SSH、DER、WPP、ERP、Case、模型版本）共享 `provenance_id` 链，记录“由谁/由哪一步/基于何输入产生”，支持任意对象回溯到原始证据。
2. **可信度分级**：每条知识/声明带 `confidence ∈ [verified(人工或实验证实), high(多源一致), medium(单源), hypothesis(未验证假设)]`；问答层按分级决定语气与展示。
3. **权限与安全**：角色（管理员/领域科学家/实验员/研发工程师/审计）与数据分级（公开文献/机构私有实验/设备原始数据/个人草稿）；内网部署可选；LLM 网关统一鉴权与脱敏。
4. **版本与回滚**：图谱与知识库按“原子提交+快照”管理；模型注册中心版本化；Case 不可变（append-only），修订通过新版本表达。
5. **可观测性**：Agent 每一步（检索、推理、工具调用）落 trace 日志，供复现、评测与审计。

## 5. 部署形态与运行环境

**目标形态（v0.9 明确）**：平台最终**部署于云端**，通过**浏览器网页（DSH Web GUI）**供多用户访问与交互——任务/问答、SSH 方案卡、干实验监视、湿实验 WPP/ERP 上传、人工仲裁、知识浏览、技能管理**全部在网页内完成**，无桌面端依赖。

- **运行底座**：DeepSeek Harness（DSH）作为多智能体运行时与 Web 壳层；模型推理默认对接 DeepSeek API/私有网关，垂域模型（微调/代理/PINN）作为 DSH 可调用工具与模型资源接入（详见 04/08）。
- **云档决策（规模由小到大平滑升级）**：

| 云档 | 适用规模 | 部署形态 | 存储档位 |
|---|---|---|---|
| A 单副本起步 | ≤10 并发、团队内 | 云主机/单容器 + HTTPS 反代 | 档位1（SQLite + FAISS + 本地卷，须持久卷与自动备份） |
| B 机构生产 | 数十~数百用户 | 容器多副本（docker-compose → K8s） | 档位2（托管/自建 PostgreSQL + 对象存储 S3/MinIO + Qdrant） |
| **C 大规模（本平台目标）** | 多团队/多场景、HA | **K8s 多副本 + Ingress/HTTPS + SSO** | 档位2 为主，按规模启用档位3（图库/时序/Kafka） |

- **运行形态要点（云档 C）**：托管数据库/对象存储/向量库；应用无状态多副本（会话外置到共享存储）；干实验 = 云端弹性 worker（CPU/GPU/HPC 池）；模型推理 DeepSeek API → 私有 vLLM 演进；多用户/多细分场景以“领域包”插拔（02 的 EDDO 扩展机制）。
- **网页交互与数据回传**：湿实验由人执行后经**浏览器网页**上传 ERP（结构化表单 + 附件 + 曲线校验；大文件走对象存储**预签名直传**）；LabLink 设备直采经云端入口（见 06）。
- **云端运维清单**：HTTPS 网关与证书（自动续期）；持久卷与**自动备份/快照**（结构化库、向量索引、文件、记忆事件）；监控告警（Prometheus/Grafana + DSH trace）；密钥与凭据管理；多副本下的会话与数据隔离（RBAC/数据分级，§4）；SSO 对接（Keycloak → 机构 IdP）；成本配额与弹性伸缩。

### A.5 数据对象与存储

- 统一数据对象：USDO、SSH、DER、WPP、ERP、Case（见 A.1）。
- 存储**三载体**（v0.8 极简档位1：FAISS + SQLite 单文件 + 本地文件目录；**用于本地开发/云档A 单副本起步**；云端生产默认升档位2，见 08 §4）：
  1. **向量索引 FAISS**：USDO/语料/记忆摘要向量与跨模态互检（payload 轻过滤经 ID 映射：usdo_id / modality / quality / confidence / source_id）；
  2. **结构化库 SQLite（单文件）**：元数据、EDDO 图谱（实体/关系/断言 = 关系表 + JSON 列，SQL 精确查询与冲突检测）、schema 注册、版本/快照、任务、权限、审计，以及记忆事件（OpRecord/SessionRecord/反思摘要，append-only）；
  3. **本地文件目录 data/**：原始载荷（PDF/图谱/图像/仿真网格/过程时序文件），内容寻址、只读不可变。
- 过程高频时序数据不独立设库：文件/parquet 归档 + SQLite 元数据。档位1 中“图”由 SQLite 关系表实现（精确查询/冲突检测/版本均可）。
- **升级路径（档位1 → 2 → 3）**：仅替换存储适配层——档位2 = Qdrant + PostgreSQL 单库 + MinIO/本地（v0.7 方案）；档位3 再评估独立图库/时序库/消息队列。L2 业务接口与检索语义不变。**云端生产（云档B/C）默认采用档位2（托管 PostgreSQL + 对象存储 S3/MinIO + Qdrant），多副本场景不用 SQLite/本地 FAISS。**

### A.6 证据与可信度标记
